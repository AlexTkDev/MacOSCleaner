How to reclaim disk space from old project build folders on Mac

Measure regenerable trees under your projects root, age-filter, move selected folders to Trash — leave active work alone

Updated 2026-10-01

Every clone that ran npm install, cargo build, or a Python venv leaves a regenerable tree next to the source. After a year of side projects, those node_modules, Rust target, .venv, Flutter .dart_tool, and generic build folders can dominate Storage even though none of them are “mystery system data.” The safe loop is: scope a projects root you choose, measure with find and du, age-filter abandoned trees (30 / 60 / 90 / 180 days), then move selected folders to Trash. Leave repos you opened this week alone. Keep source, lockfiles, and .git. Do not disable SIP. Do not wipe Docker.raw or run a whole-home find … -exec rm.

Two buckets: project folders vs global caches

(A) Per-project artifacts live inside a repo: node_modules, Rust target, Python .venv / venv, Flutter/Dart .dart_tool, and regenerable build / dist when your toolchain can recreate them from source and lockfiles. These are usually the largest reclaimable trees on a developer Mac.

(B) Global package caches are shared download stores — npm’s cache, Yarn’s cache, the pnpm store. Cleaning them is a smaller, secondary win and uses each tool’s own CLI (covered briefly below). This guide focuses on bucket A. Homebrew bottles are a separate path — measure and clean them with brew cleanup (see the package-cache step in the System Data reclaim order guide until a dedicated Homebrew page is live).

Scope the scan to a projects root

Pick one root you control — commonly ~/Developer, ~/Projects, or ~/src. Restrict the search there so you never walk ~/Library, ~/.Trash, system prefixes, or unrelated home clutter. When find hits a matching folder name, prune so it does not recurse into every nested package inside node_modules (that wastes time and double-counts noise).

zsh — set a projects root
# change this to the folder that holds your repos
$ PROJECTS="$HOME/Developer"
$ ls "$PROJECTS"

Measure with find + du (dry-run list)

List candidates and sizes first. Nothing below deletes files — it only prints paths and disk use. Adjust names if your stack uses different conventions (for example venv instead of .venv).

zsh — list sizes (measure only)
$ find "$PROJECTS" -type d \( \
  -name node_modules -o -name target -o \
  -name .venv -o -name venv -o \
  -name .dart_tool -o -name build \) \
  -prune -exec du -sh {} +

Age filter next. -mtime +N keeps directories whose contents were last modified more than N days ago — the same windows many people use for abandoned work: 30, 60, 90, or 180 days. Start conservative (e.g. 90) if you reopen old repos often.

zsh — older than 90 days
# change +90 to +30, +60, or +180 as needed
$ find "$PROJECTS" -type d \( \
  -name node_modules -o -name target -o \
  -name .venv -o -name venv -o \
  -name .dart_tool -o -name build \) \
  -mtime +90 -prune -print

Treat build and dist carefully: some projects store non-regenerable assets under those names. Prefer deleting only when you know the toolchain recreates the folder (e.g. a Flutter/Gradle/webpack output you can rebuild), or skip those names and stick to node_modules / target / .venv / .dart_tool.

Review the list before anything moves

  • Skip any repo you opened or built this week — even if the folder name matches.
  • Keep source trees, package.json / Cargo.toml / pyproject.toml / pubspec.yaml, lockfiles, and the entire .git directory.
  • Candidates are regenerable sibling folders only: install trees and compiler outputs you can recreate from those manifests.
  • Monorepos: several node_modules may appear; prune still stops recursion into each one — review package paths before moving them.

Remove safely: Trash selected folders

Prefer Trash over permanent rm -rf so Finder → Put Back can undo a mistake. Move one reviewed path at a time — never pipe a bulk find into rm.

zsh — Trash one folder you already reviewed
# EXAMPLE only — replace with a path from YOUR review list
$ FOLDER="$PROJECTS/old-api/node_modules"
$ test -d "$FOLDER" && mv "$FOLDER" ~/.Trash/
# or: Finder → move the folder to Trash

Do not run whole-home find ~ … -exec rm -rf {} +, delete package.json / lockfiles, or wipe active project trees “to be thorough.” Empty Trash only after you are sure nothing important landed there.

Restore / rebuild when you reopen a project:

zsh — typical reinstall / rebuild
$ npm ci              # or: yarn / pnpm install
$ cargo build          # recreates target/
$ python3 -m venv .venv && . .venv/bin/activate
$ flutter pub get      # recreates .dart_tool

Optional secondary: global package caches

After old project folders, shared caches can free a bit more space. Measure with each tool’s path command first — do not guess store locations. Official CLIs:

zsh — global caches (secondary)
$ du -sh "$(npm config get cache)"
# npm docs: clean needs --force to reclaim space
$ npm cache clean --force
$ yarn cache clean            # classic / Berry local
$ yarn cache clean --all       # Berry: local + global
$ du -sh "$(pnpm store path)"
$ pnpm store prune           # unreferenced packages only

npm’s docs note the cache is self-healing; npm cache clean requires --force specifically when the goal is reclaiming disk space. Yarn Berry’s --all removes both the project-local cache and the global mirror files. pnpm store prune drops packages no project still references — safe, but future installs may re-download. None of these replace removing abandoned node_modules trees.

What not to delete

  • Active project trees — anything you still open weekly; skip it even if the age filter matches a nested cache.
  • Docker.raw / Docker Desktop data — not a project build folder; reclaim with Docker’s own prune flow in the Docker disk space guide. Never wipe the raw disk file by hand.
  • SIP / /System / /usr — unrelated to node_modules; disabling SIP will not help and is unsafe.
  • SSH keys and secrets — never touch ~/.ssh or credential stores while “cleaning disk.”
  • Xcode Archives / dSYMs / DerivedData — different tools; see Xcode caches.
  • Homebrew Cellar — uninstall with brew uninstall / clean with brew cleanup; do not delete Cellar folders by hand (package-cache notes in System Data reclaim order).

Frequently asked questions

Is it safe to delete node_modules on Mac?
Yes for regenerable install trees you no longer need, as long as you keep package.json and the lockfile. Reinstall with npm ci, yarn install, or pnpm install. Prefer Trash over permanent delete. Do not remove source or lockfiles.
What is the difference between npm cache and node_modules?
node_modules is per-project next to your app. The npm cache is a shared download store — locate it with npm config get cache (often ~/.npm). Clearing the cache is a secondary win; old project folders usually free more space.
Will deleting build folders break git?
No, if you only remove regenerable, typically gitignored folders and leave .git, source, and lockfiles alone. Deleting .git or tracked files would break the repo — that is not part of this cleanup.
Why use an age filter (30 / 60 / 90 / 180 days)?
find -mtime +N surfaces folders you have not touched recently, so active work stays off the list. Pick a larger N if you jump between old branches often; tighten it only after reviewing a dry-run list.
Do I need to disable SIP to clean project build folders?
No. These folders live under your home directory in repos you own. Do not disable SIP and do not delete anything under /System or /usr for this task.
