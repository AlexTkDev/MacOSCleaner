Mac storage not freeing up? Time Machine local snapshots and purgeable space

Why deleted files can keep using space on APFS, how to read the purgeable number, and how to thin snapshots instead of wiping them

Updated 2026-10-05

You delete a 40 GB VM image or an old Xcode archive, empty the Trash, and Storage barely moves. Or Finder says you have plenty of room while an installer insists the disk is full. On a Mac with an APFS startup disk and Time Machine turned on, the usual cause is local snapshots: point-in-time copies that keep referencing data you already deleted, which macOS reports as purgeable space. The safe loop is: empty the Trash, read the right free-space number, list snapshots with tmutil, then thin them to a byte target. Do not wipe every snapshot, do not touch macOS update snapshots, and do not disable SIP.

Why deleted files can keep using space

APFS snapshots are cheap because they share blocks with the live disk. The catch is that when you delete a file, any snapshot taken before the delete still points at those blocks, so the space is not returned until that snapshot goes away.

When Time Machine is set up, macOS keeps local snapshots on the startup disk so you can restore recent changes even when the backup drive isn’t connected. Apple describes them as hourly snapshots kept for about 24 hours, plus a snapshot of the last successful backup kept until space is needed. macOS removes them on its own as they age or when the disk gets tight, which is why the space is labelled purgeable rather than used.

  • Still in the Trash? Files in the Trash count as used space. Empty it first.
  • Held by a snapshot? The blocks come back when the snapshot expires or is thinned.
  • Shown as purgeable? The space is reclaimable, but some tools don’t treat it as free yet.

Read the right free-space number

Different parts of macOS answer “how much space is free?” differently. Finder’s Get Info on your startup disk shows Available with the purgeable part in brackets, for example “Available: 120 GB (35 GB purgeable)”. df in Terminal shows only plain free space, without purgeable.

zsh — compare free space (read only)
$ df -h /
# Avail here excludes purgeable space
# compare with Finder: select Macintosh HD, File, Get Info

If Finder shows a large purgeable figure and df shows much less, snapshots or other purgeable data are the gap. That gap is also why an installer, a VM tool, or a command-line program can refuse to run: many of them check plain free space only. For developers: Apple’s volumeAvailableCapacityForImportantUsageKey includes space the system can purge, while volumeAvailableCapacityKey does not, so two apps can honestly report different numbers for the same disk.

List local snapshots

These commands only read. They show the Time Machine snapshots on the startup disk, named by date and time.

zsh — list local snapshots (read only)
$ tmutil listlocalsnapshots /
# e.g. com.apple.TimeMachine.2026-10-05-093015.local
$ tmutil listlocalsnapshotdates /

An empty list means snapshots aren’t your problem; skip ahead to the last step. Seeing a few snapshots from the last day is normal and healthy. tmutil doesn’t print a size per snapshot, because snapshots share blocks with each other and with the live disk; Finder’s purgeable figure is the practical estimate.

If you also run diskutil apfs listSnapshots /, you may see a snapshot named like com.apple.os.update-…. That one belongs to macOS itself and is used for the signed system volume and updates. Leave it alone.

Thin snapshots to a byte target

tmutil thinlocalsnapshots asks macOS to remove snapshots it already considers purgeable until it frees the amount you request. It takes a mount point, a target in bytes, and an urgency from 1 (gentle) to 4 (most aggressive). Shell arithmetic saves you from counting zeros.

zsh — thin local snapshots
# ask for about 20 GB at urgency 4
$ tmutil thinlocalsnapshots / $((20 * 1024 * 1024 * 1024)) 4
# if it reports a permission error, run the same line with sudo
$ tmutil listlocalsnapshots /
$ df -h /

Pick a target close to what you actually need, such as the size of the install that failed plus some headroom. macOS may free less than you ask for if the remaining snapshots aren’t purgeable yet, and it may keep the newest ones. That’s by design: thinning gives back space without throwing away every recent restore point. Your backups on the external Time Machine disk are not affected.

If thinning freed little, look elsewhere

When the snapshot list was short or thinning barely changed df, the space is held by real files, not snapshots. On a developer Mac the usual suspects are Xcode data, Docker’s disk image, simulator runtimes, and package or IDE caches, all of which Storage lumps into System Data. Measure before you remove anything, and work through them in order: see System Data reclaim order, Xcode caches, and Docker disk space.

One more APFS quirk worth knowing: right after a big cleanup, free space can lag for a few minutes while macOS finishes reclaiming blocks. Check again before trying anything drastic.

What not to do

  • Don’t wipe the whole snapshot set. Thinning is enough almost every time, and deleting everything removes your safety net for mistakes made since the last backup.
  • Don’t delete com.apple.os.update-… or other system snapshots with diskutil. They aren’t Time Machine clutter.
  • Don’t disable SIP or delete anything under /System. It won’t shrink snapshots and it weakens the Mac’s security.
  • Don’t follow old guides that mention tmutil disablelocal or a /.MobileBackups folder. Those come from pre-APFS macOS and don’t apply to current systems.
  • Don’t turn Time Machine off just to free space. Local snapshots are temporary by design, and the backups matter more than a few gigabytes.
  • Don’t delete Docker.raw by hand when the real space hog turns out to be Docker. Use Docker’s own cleanup instead (see Docker disk space).

Frequently asked questions

Why didn’t my Mac free up space after I deleted files?
Three usual reasons: the files are still in the Trash, a local Time Machine snapshot still references the deleted data, or the space was freed but shows up as purgeable instead of plain free space. Empty the Trash, then check for local snapshots with tmutil listlocalsnapshots / and thin them if needed.
What does purgeable space mean on a Mac?
Purgeable space is storage macOS can reclaim on its own when something needs room, such as local Time Machine snapshots and some cached or iCloud-optimized content. Finder’s Get Info shows it in brackets next to Available. Command-line tools like df do not count it as free.
Is it safe to thin Time Machine local snapshots?
Yes. tmutil thinlocalsnapshots asks macOS to remove snapshots it already considers purgeable until it reaches the byte target you give it. You lose some recent restore points, but your backups on the Time Machine disk are not touched.
Should I delete all local snapshots?
No. Thinning is enough in almost every case and keeps the newest restore points. Deleting the whole set removes your safety net for accidental deletions between backups, and some snapshots, such as macOS update snapshots, are part of how the system works and should be left alone.
Why does an installer say there isn’t enough space when Finder shows plenty?
Finder’s Available figure includes purgeable space. Some installers, VM tools, and command-line programs only look at the plain free space, which excludes it. Thinning local snapshots turns purgeable space into regular free space those tools can see.
Do I need to disable SIP to remove snapshots?
No. tmutil is a standard macOS tool and works with SIP on. Do not disable SIP or delete anything under /System to free space.
